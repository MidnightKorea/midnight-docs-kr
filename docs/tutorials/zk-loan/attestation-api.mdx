# Attestation API

[컨트랙트](/tutorials/zk-loan/smart-contract)는 등록된 provider가 서명한 신용 프로필만 신뢰합니다.
이 파트에서는 그 provider, 즉 `examples/zk-loan/attestation-api/`의 attestation API를 살펴봅니다.
Jubjub 곡선 위의 Schnorr signature로 신용 데이터에 서명하는 작은 REST 서버입니다. 실제 환경에서는
은행이나 신용평가 기관의 서비스가 되겠지만, 여기서는 그것을 대신합니다.

## Prerequisites

- 이 튜토리얼의 [ZK Loan contract](/tutorials/zk-loan/smart-contract) 파트.

## The endpoints

이 API에는 세 개의 endpoint가 있습니다:

- `POST /attest`는 신용 데이터와 차입자 신원의 해시를 받아, 그에 대한 Schnorr signature를 반환합니다.
- `GET /provider-info`는 provider의 ID와 public key를 반환합니다. admin은 이를 `registerProvider`로
  온체인에 등록합니다.
- `GET /health`는 서버 상태를 반환합니다.

## Wire types

`attestation-api/types.ts`는 요청과 응답의 형태를 정의합니다:

```typescript title="attestation-api/types.ts"
// Wire types for the attestation API. JSON has no bigint, so every field-sized
// value travels as a decimal string; clients convert with BigInt(...).

export interface AttestationRequest {
  creditScore: number;
  monthlyIncome: number;
  monthsAsCustomer: number;
  // transientHash(deriveUserPublicKey(secret, pin)) as a decimal string. The
  // borrower computes it locally, so the API never learns the secret or PIN.
  userPubKeyHash: string;
}

export interface AttestationResponse {
  signature: {
    announcement: { x: string; y: string };
    response: string;
  };
  message: {
    creditScore: string;
    monthlyIncome: string;
    monthsAsCustomer: string;
    userPubKeyHash: string;
  };
}

export interface ProviderInfoResponse {
  providerId: number;
  publicKey: { x: string; y: string };
}

export interface HealthResponse {
  status: string;
  providerId: number;
}
```

- `AttestationRequest`는 신용 데이터를 숫자로, `userPubKeyHash`를 문자열로 받습니다. 이 해시는 field
  원소라 JSON 숫자로 담기엔 너무 크므로, 십진 문자열로 전달됩니다.
- `AttestationResponse`는 같은 이유로 서명의 announcement 점과 response 스칼라를 문자열로
  반환합니다. `message`는 서명된 내용을 그대로 돌려줍니다.

차입자는 자신의 secret과 PIN에서 `userPubKeyHash`를 로컬로 계산하므로, provider는 둘 중 어느 것도
알지 못합니다.

## Signing

`attestation-api/signing.ts`는 `contract/schnorr.compact`의 오프체인 쪽 절반입니다. 두 개의 상수로
시작합니다. Jubjub 부분군의 위수와, challenge 잘라내기에 쓰는 2^248입니다.

```typescript title="attestation-api/signing.ts"
import * as crypto from 'node:crypto';
import { ecMulGenerator, type JubjubPoint } from '@midnight-ntwrk/midnight-js-protocol/compact-runtime';
import { pureCircuits, type Schnorr_SchnorrSignature } from '../contract/index.js';

// Order of the Jubjub prime-order subgroup. Scalars passed to ecMulGenerator
// must be below this or it throws "out of bounds for prime field".
export const JUBJUB_ORDER = 6554484396890773809930967563523245729705921265872317281365359162392183254199n;
// The circuit truncates the BLS12-381 challenge hash to 248 bits so it is a
// valid Jubjub scalar; the signer must truncate the same way.
export const TWO_248 = 452312848583266388373324160190187140051835877600158453279131187530910662656n;

const reduce = (x: bigint): bigint => ((x % JUBJUB_ORDER) + JUBJUB_ORDER) % JUBJUB_ORDER;
```

서명자는 `contract/index.ts`에서 `pureCircuits`를 import합니다. 이는 컴파일러가 컨트랙트의 pure
circuit에서 생성한 TypeScript이며, `schnorrChallenge`도 여기에 포함됩니다.

키 생성은 Jubjub 위수보다 작은 무작위 스칼라를 고릅니다:

```typescript title="attestation-api/signing.ts"
// A uniformly-ish random scalar. 256 random bits reduced mod the ~2^252 order
// has negligible bias for a demo; a production signer would use rejection
// sampling and HSM-held keys.
function randomScalar(): bigint {
  return BigInt('0x' + crypto.randomBytes(32).toString('hex')) % JUBJUB_ORDER;
}

export function generateKeyPair(): { sk: bigint; pk: JubjubPoint } {
  const sk = randomScalar();
  return { sk, pk: ecMulGenerator(sk) };
}

export function getPublicKey(sk: bigint): JubjubPoint {
  return ecMulGenerator(reduce(sk));
}
```

그다음은 서명 자체입니다:

```typescript title="attestation-api/signing.ts"
// Sign a 4-element message. The nonce k is fresh per signature — reusing a
// nonce across two messages leaks the secret key.
export function sign(sk: bigint, msg: bigint[]): Schnorr_SchnorrSignature {
  sk = reduce(sk);
  const pk = ecMulGenerator(sk);
  const k = randomScalar();
  const R = ecMulGenerator(k);
  // pureCircuits.schnorrChallenge returns the full transientHash output; the
  // circuit reduces it mod 2^248 before the EC ops, so do the same here.
  const c = pureCircuits.schnorrChallenge(R.x, R.y, pk.x, pk.y, msg) % TWO_248;
  // s must be reduced mod the Jubjub order (not the BLS12-381 field), because
  // the circuit feeds it to ecMulGenerator.
  const s = reduce(k + c * sk);
  return { announcement: R, response: s };
}
```

단계별로 보면:

1. `reduce`로 비밀 키를 Jubjub 스칼라 field로 줄입니다. `ecMulGenerator`는 Jubjub 위수보다 작은
   스칼라만 받고, 그렇지 않으면 "out of bounds for prime field" 오류를 던집니다. 그래서 보통 위수보다
   큰 임의의 32바이트 값에서 로드한 키도 정상 동작합니다.
2. 새로운 무작위 nonce `k`를 고르고, announcement `R = k*G`를 계산합니다.
3. circuit이 쓰는 것과 같은 해시인 `pureCircuits.schnorrChallenge`로 challenge를 계산하고,
   248비트로 잘라냅니다.
4. response `s = k + c*sk`를 계산하되 Jubjub 위수를 법으로 줄입니다. circuit이 `s`를
   `ecMulGenerator`에 넘기기 때문입니다.

그러면 circuit은 `s*G == R + c*pk`를 검사합니다. 3단계가 핵심입니다. 서명자가 컨트랙트가 직접
컴파일한 `schnorrChallenge`를 호출하므로, circuit과 똑같은 해시를 계산합니다. 다른 해시를 썼다면 모든
서명이 검증에 실패했을 것입니다.

:::caution
nonce를 재사용하지 마세요. 같은 `k`로 서로 다른 메시지에 서명한 두 서명은 비밀 키를 드러냅니다.
`sign`은 매번 새 `k`를 뽑습니다.
:::

`signCreditData`는 `evaluateApplicant`이 circuit 안에서 다시 만드는 것과 정확히 같은 배치로 메시지를
구성합니다:

```typescript title="attestation-api/signing.ts"
// The exact message layout `evaluateApplicant` rebuilds in-circuit:
// [creditScore, monthlyIncome, monthsAsCustomer, userPubKeyHash]. The last
// element binds the attestation to one borrower identity, so it cannot be
// replayed by anyone else.
export function signCreditData(
  sk: bigint,
  creditScore: number | bigint,
  monthlyIncome: number | bigint,
  monthsAsCustomer: number | bigint,
  userPubKeyHash: bigint,
): Schnorr_SchnorrSignature {
  return sign(sk, [BigInt(creditScore), BigInt(monthlyIncome), BigInt(monthsAsCustomer), userPubKeyHash]);
}
```

마지막 원소 `userPubKeyHash`는 서명을 하나의 차입자 신원에 묶습니다. 다른 차입자는 자신의 신원이 다른
값으로 해시되므로 이 서명을 재사용할 수 없습니다.

## The REST server

`attestation-api/server.ts`는 endpoint를 서명자에 연결합니다. [Restify](https://restify.com/)를
사용하고 모든 origin을 허용하므로, 브라우저 DApp이 직접 호출할 수 있습니다:

```typescript title="attestation-api/server.ts"
export function createServer(providerSk: bigint, providerId: number): restify.Server {
  const server = restify.createServer({ name: 'zkloan-attestation-api' });
  server.use(restify.plugins.bodyParser());

  // Permissive CORS so a browser DApp can call the API directly.
  server.pre((req: restify.Request, res: restify.Response, next: restify.Next) => {
    res.header('Access-Control-Allow-Origin', '*');
    res.header('Access-Control-Allow-Methods', 'GET, POST, OPTIONS');
    res.header('Access-Control-Allow-Headers', 'Content-Type');
    if (req.method === 'OPTIONS') {
      res.send(204);
      return next(false);
    }
    return next();
  });

  const providerPk: JubjubPoint = getPublicKey(providerSk);
```

`POST /attest`는 네 필드가 모두 있는지 확인하고, provider의 비밀 키로 서명한 뒤, 모든 bigint을 십진
문자열로 담아 서명과 서명된 메시지를 반환합니다:

```typescript title="attestation-api/server.ts"
  server.post('/attest', (req: restify.Request, res: restify.Response, next: restify.Next) => {
    try {
      const body = req.body as AttestationRequest;

      if (
        body?.creditScore == null ||
        body.monthlyIncome == null ||
        body.monthsAsCustomer == null ||
        body.userPubKeyHash == null
      ) {
        res.send(400, {
          error: 'Missing required fields: creditScore, monthlyIncome, monthsAsCustomer, userPubKeyHash',
        });
        return next();
      }

      const userPubKeyHash = BigInt(body.userPubKeyHash);
      const signature = signCreditData(
        providerSk,
        body.creditScore,
        body.monthlyIncome,
        body.monthsAsCustomer,
        userPubKeyHash,
      );

      const response: AttestationResponse = {
        signature: {
          announcement: {
            x: signature.announcement.x.toString(),
            y: signature.announcement.y.toString(),
          },
          response: signature.response.toString(),
        },
        message: {
          creditScore: body.creditScore.toString(),
          monthlyIncome: body.monthlyIncome.toString(),
          monthsAsCustomer: body.monthsAsCustomer.toString(),
          userPubKeyHash: userPubKeyHash.toString(),
        },
      };
      res.send(200, response);
    } catch (err) {
      res.send(500, { error: err instanceof Error ? err.message : String(err) });
    }
    return next();
  });
```

`GET /provider-info`는 admin이 이 provider를 온체인에 등록하는 데 필요한 값을 반환하고,
`GET /health`는 표준 health check입니다:

```typescript title="attestation-api/server.ts"
  server.get('/provider-info', (_req: restify.Request, res: restify.Response, next: restify.Next) => {
    const response: ProviderInfoResponse = {
      providerId,
      publicKey: { x: providerPk.x.toString(), y: providerPk.y.toString() },
    };
    res.send(200, response);
    return next();
  });

  server.get('/health', (_req: restify.Request, res: restify.Response, next: restify.Next) => {
    const response: HealthResponse = { status: 'ok', providerId };
    res.send(200, response);
    return next();
  });

  return server;
}
```

:::warning Demo-grade
이 서버는 받은 신용 데이터라면 무엇이든 서명합니다. 실제 provider라면 요청 본문을 믿는 대신 호출자를
인증하고 수치를 자체 기록에서 조회할 것입니다. 컨트랙트는 *이* provider가 데이터를 보증했다는 것만
증명하므로, provider가 신뢰의 기준점입니다.
:::

## The entry point

`attestation-api/index.ts`는 provider 키를 로드하거나 생성하고 서버를 시작합니다:

```typescript title="attestation-api/index.ts"
setNetworkId(process.env['NETWORK_ID'] || 'undeployed');

const PORT = parseInt(process.env['PORT'] || '4000', 10);
const PROVIDER_ID = parseInt(process.env['PROVIDER_ID'] || '1', 10);

let providerSk: bigint;
const secretHex = process.env['PROVIDER_SECRET_KEY'];
if (secretHex) {
  // Reduce so any 32-byte hex value is a valid Jubjub scalar.
  providerSk = BigInt('0x' + secretHex) % JUBJUB_ORDER;
  console.log('Loaded provider secret key from environment');
} else {
  providerSk = generateKeyPair().sk;
  console.log('Generated ephemeral provider key pair');
}

const pk = getPublicKey(providerSk);
console.log(`Provider ID: ${PROVIDER_ID}`);
console.log('Provider public key:');
console.log(`  x: ${pk.x}`);
console.log(`  y: ${pk.y}`);
console.log(`Register this provider on-chain with: registerProvider(${PROVIDER_ID}, {x: ${pk.x}n, y: ${pk.y}n})`);

createServer(providerSk, PROVIDER_ID).listen(PORT, () => {
  console.log(`Attestation API listening on port ${PORT}`);
});
```

환경 변수 네 개를 읽습니다:

- `PORT`: 리스닝 포트. 기본값 4000.
- `PROVIDER_ID`: 키가 등록되는 온체인 ID. 기본값 1.
- `PROVIDER_SECRET_KEY`: 16진수 Jubjub 비밀 키. 이 값이 없으면 서버는 시작할 때마다 새 키를
  생성하고, 그 키를 다시 온체인에 등록해야 합니다. 이 값이 있으면 public key가 재시작을 거쳐도
  동일하게 유지됩니다. 무작위 32바이트 값은 대부분 위수보다 크므로, 이 값은 먼저 Jubjub 위수를 법으로
  줄여집니다.
- `NETWORK_ID`: 기본값은 로컬 네트워크인 `undeployed`입니다. `preprod` 같은 다른 네트워크를 대상으로
  하려면 설정하세요.

## The attestation flow

세 당사자에 걸쳐 attestation이 어떻게 동작하는지 보면 다음과 같습니다:

```plaintext
┌──────────┐     ┌────────────────┐     ┌───────────────┐
│ Borrower │     │  Attestation   │     │   Midnight    │
│ (DApp)   │     │      API       │     │   Network     │
└────┬─────┘     └───────┬────────┘     └───────┬───────┘
     │                   │                      │
     │  1. Admin registers provider PK on-chain │
     │─────────────────────────────────────────>│
     │                   │                      │
     │  2. POST /attest  │                      │
     │  {creditScore,    │                      │
     │   monthlyIncome,  │                      │
     │   monthsAsCustomer│                      │
     │   userPubKeyHash} │                      │
     │──────────────────>│                      │
     │                   │                      │
     │  3. Returns signed│                      │
     │  Schnorr signature│                      │
     │<──────────────────│                      │
     │                   │                      │
     │  4. Submit loan request with signature   │
     │  (signature in private state, never      │
     │   visible on-chain)                      │
     │─────────────────────────────────────────>│
     │                   │                      │
     │                   │  5. ZK circuit       │
     │                   │  verifies signature  │
     │                   │  against registered  │
     │                   │  PK (all in zero-    │
     │                   │  knowledge)          │
     │                   │                      │
     │  6. Only loan status + amount on ledger  │
     │<─────────────────────────────────────────│
```

1. **provider 등록.** admin이 `registerProvider`를 호출해 API의 public key를 컨트랙트의
   `providers` map에 저장합니다. 설정 단계 중 체인에 닿는 것은 이 단계뿐입니다.
2. **attestation 요청.** 차입자는 private state의 secret과 PIN에서 `deriveUserPublicKey` pure
   circuit으로 신원을 도출한 뒤 이를 해시합니다. 그 해시와 신용 데이터를 API로 보냅니다.
3. **서명과 반환.** API는 네 값을 하나의 Schnorr signature로 서명합니다. 신원 해시를 포함하면
   attestation이 이 차입자에 묶입니다.
4. **대출 요청 제출.** 차입자는 서명을 private state에 저장하고 `requestLoan`을 호출합니다. 서명은
   witness의 일부로 proof server에 전달됩니다. 체인에 도달하는 트랜잭션에는 결코 나타나지 않습니다.
5. **ZK에서 검증.** circuit 안에서 `evaluateApplicant`이 witness에서 서명을 가져오고, ledger에서
   provider의 public key를 조회한 뒤 `schnorrVerify`를 실행합니다. 데이터가 변조됐거나, 다른
   provider가 서명했거나, attestation이 다른 사람의 것이면 assert가 실패하고 트랜잭션이 제출되지
   않습니다.
6. **결과 기록.** 대출의 status와 승인 금액만 ledger에 기록됩니다. 신용 점수, 소득, 재직 기간, PIN,
   서명은 비공개로 유지됩니다.

각 당사자가 알게 되는 것:

- **차입자는 거짓말할 수 없다.** 컨트랙트가 circuit 안에서 provider의 서명을 검증하므로, 지어낸 신용
  데이터는 실패합니다.
- **체인은 결과만 안다.** 신용 데이터와 서명은 proof의 private 입력입니다. 관찰자는 도출된 key 아래의
  대출 status와 금액만 볼 뿐, 그 외에는 아무것도 보지 못합니다.
- **provider는 자신이 서명하는 것을 보며, 그것을 연결할 수 있다.** provider는 이미 그 수치를 알고
  있습니다. 바로 그 출처이기 때문입니다. 차입자의 secret이나 PIN은 결코 알지 못합니다. 하지만
  `userPubKeyHash`는 차입자가 도출한 key의 단순 해시이고, 그 key는 `loans`에 공개되어 있습니다.
  따라서 ledger를 지켜보는 provider는 자신의 attestation을 차입자의 대출과 맞춰 볼 수 있습니다.
